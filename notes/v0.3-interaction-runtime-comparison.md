# v0.3 交互动效运行时对比

## 核心问题

原生 CSS/SVG 应该在哪里停止继续扩展？Motion 在什么情况下是最合适的
React 抽象？GSAP 的显式时间轴控制在什么时候值得付出额外成本？

## 统一实验协议

- 三种运行时共用同一棵 `BenchmarkScene` DOM 与 SVG 结构。
- 共用一个 7.2 秒的 Collect → Resolve → Decide 产品叙事。
- 共用播放、暂停、重播、反向、定位、视口和减弱动态效果控制。
- 提供横向、方形与竖向三种舞台预设。
- 每 100 毫秒采样一次播放进度，避免遥测在每个动画帧触发 React 渲染。
- 启用减弱动态效果后直接进入信息完整的最终状态。
- 运行时代码只存在于对应演示路由；GSAP 在客户端组件挂载后通过动态
  import 加载。

## 生产构建数据

数据通过 2026-08-09 的 `pnpm build` 测得。下表是排除共享应用外壳后，
每个路由独占 chunk 的 gzip 体积。它衡量的是完整参考实现而不是孤立的库，
chunk hash 因不稳定而不记录。

| 运行时 | 路由独占产物 | 驱动层规模 | 播放控制桥接方式 |
|---|---:|---:|---|
| CSS + SVG | 约 0.9 kB gzip | 155 行 TSX，另有共享场景样式表中的原生关键帧 | Web Animations API |
| Motion | 约 52 kB gzip | 198 行 TSX | `useAnimate` 播放控制器 |
| GSAP | 首屏约 1.3 kB + 懒加载约 27 kB gzip | 224 行 TSX | 带标签的 `gsap.timeline()` |

行数包含初始化和清理逻辑，因此只代表维护成本信号，不是代码高尔夫得分。
原生 CSS 的运行时产物最小，但会把编排成本转移到冗长的百分比关键帧中。
Motion 路由还同时验证了手势、共享布局与挂载状态，所以参考路由成本最高。
GSAP 只在对应路由挂载后加载时间轴引擎。

## 浏览器验证

在仓库默认地址 `http://localhost:4394`，使用 Codex 内置 Chromium 浏览器验证：

- 所有运行时：重播、暂停、键盘定位、反向播放和减弱动态效果。
- 原生方案：主时间轴过滤掉独立的实时指示器脉冲动画。
- Motion：手势反馈、共享布局指示器和可中断的 `AnimatePresence` 内容。
- GSAP：命名阶段、交错、SVG 路径绘制、反向播放和动态加载。
- 响应式：390 × 844 视口下没有文档级横向溢出。
- 可访问性：播放控制和滑块有明确名称、状态控件可用键盘操作、叙事文本保持
  语义化、SVG 提供替代说明。
- 控制台：验证流程中没有 warning 或 error。

## 技术结论

### 默认方案：原生 CSS + SVG

持久的 UI 状态反馈、短小的状态驱动序列和矢量细节优先使用浏览器原生
transition 与关键帧。只有小型原生编排需要播放控制时，才加入 Web Animations
API。一旦阶段关系成为主要维护难点，就不应继续扩展百分比关键帧。

### React 升级方案：Motion

当 React 状态拥有动画职责时使用 Motion，包括手势、组件挂载状态、布局过渡、
共享元素、弹簧和中断。不应在单一 CSS transition 已能清楚表达关系时引入它；
如果编辑型主时间轴才是核心产物，也不应强行使用 Motion。

### 编排升级方案：GSAP

当命名提示点、高密度重叠、跨 DOM/SVG 图层协调、拖动定位、反向播放和频繁
重排节奏证明了显式时钟的价值时使用 GSAP。依赖必须保持路由隔离与懒加载。
不要把 GSAP 当作通用 React 状态抽象，也不要让它和其他运行时竞争写入同一个
transform。

## 组合规则

三种运行时是逐级升级关系，而不是只能三选一的项目级竞争者。在混合方案中，
每个属性和图层都必须只有一个所有者：CSS 负责持久状态反馈，Motion 负责 React
交互，GSAP 负责明确设计的主时间轴。两个运行时绝不能同时写入同一个 transform。
