# v0.3 interaction runtime comparison

## Question

Where should native CSS/SVG stop, where does Motion provide the best React
abstraction, and when does GSAP's explicit timeline control justify its cost?

## Shared protocol

- One `BenchmarkScene` DOM and SVG tree across all runtimes.
- One 7.2 second Collect → Resolve → Decide product narrative.
- The same play, pause, replay, reverse, seek, viewport, and reduced-motion
  controls.
- Wide, square, and portrait stage presets.
- Progress sampled every 100 ms so telemetry does not trigger a React render on
  every animation frame.
- Reduced motion skips directly to the complete information state.
- Runtime code remains in its demonstrating route; GSAP is loaded with a dynamic
  import after the GSAP client component mounts.

## Production-build evidence

Measured with `pnpm build` on 2026-08-09. Values below are gzip sizes for chunks
unique to each route after the shared application shell. They measure the
reference implementation rather than a library in isolation, and chunk hashes
are intentionally omitted because they are not stable.

| Runtime | Route-only output | Driver implementation | Control bridge |
|---|---:|---:|---|
| CSS + SVG | ~0.9 kB gzip | 155 TSX lines plus native keyframes in the shared scene stylesheet | Web Animations API for transport |
| Motion | ~52 kB gzip | 198 TSX lines | `useAnimate` playback controls |
| GSAP | ~1.3 kB initial + ~27 kB lazy gzip | 224 TSX lines | labeled `gsap.timeline()` |

Line counts include setup and cleanup, so they are a maintainability signal, not
a code-golf score. Native CSS has the smallest runtime output but moves
choreography cost into verbose percentage keyframes. Motion pays the largest
reference-route cost because the same route also proves gestures, shared layout,
and presence. GSAP loads the timeline engine only after its route mounts.

## Browser verification

Verified in the Codex in-app Chromium browser at the repository's default
`http://localhost:4394` origin:

- All runtimes: replay, pause, keyboard seek, reverse, and reduced motion.
- Native: timeline filtering excludes the independent live-indicator pulse.
- Motion: gesture feedback, shared layout indicator, and interruptible
  `AnimatePresence` content.
- GSAP: labeled phases, stagger, SVG path draw, reverse, and dynamic load.
- Responsive: 390 × 844 viewport with no document-level horizontal overflow.
- Accessibility: named transport controls, named slider thumb, keyboard-operable
  state controls, semantic story copy, and SVG alternative text.
- Console: no warnings or errors during the tested flows.

## Decision

### Default: native CSS + SVG

Use native transitions and keyframes for durable UI feedback, short state-driven
sequences, and vector details. Add the Web Animations API only when a small native
composition needs transport controls. Do not keep extending percentage
keyframes once phase relationships become the main maintenance problem.

### React escalation: Motion

Use Motion when React state owns the animation: gestures, component presence,
layout transitions, shared elements, springs, and interruption. Avoid it when a
single CSS transition communicates the relationship or when an editorial master
timeline is the primary artifact.

### Choreography escalation: GSAP

Use GSAP when named cues, dense overlaps, cross-layer SVG/DOM coordination,
scrubbing, reversing, and frequent editorial retiming justify one explicit
clock. Keep it route-scoped and lazy. Avoid using it as a general React state
abstraction or letting it compete with another runtime for the same transform.

## Composition rule

The runtimes are an escalation ladder, not mutually exclusive project choices.
In hybrid work, each property and layer must have one owner: CSS for persistent
state feedback, Motion for React interaction, and GSAP for a deliberate master
timeline. Two runtimes must never write the same transform at the same time.
