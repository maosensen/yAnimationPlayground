# v0.4 数据与视觉运行时对比

## 核心问题

数据变换、设计工具导出的矢量动画、交互状态机与高密度即时绘制应如何协作，
才能避免让某一项技术承担所有职责？

## 对比实现

- D3 只负责 `array → scale → shape` 数据管线，React 持有 SVG 元素，Motion
  负责筛选状态之间的过渡。
- Lottie Light 按需加载本地 JSON 资产，验证播放、暂停、定位、marker 对应的
  三段播放、响应式 SVG 与静态模式。
- Rive Canvas Lite 加载官方车辆示例，通过 `bumpy` 状态机的 `bump` Trigger
  验证应用输入与资产内部过渡的边界。
- Canvas 使用单一绘制表面承载 120、360 或 720 个粒子；粒子与指针状态保留在
  refs，每 500ms 才把 FPS 与帧时间写入 React。
- Living Data Story 以一个 React 状态模型组合 D3 几何、Motion 过渡、Canvas
  环境层与 Lottie 状态提示，不让两个运行时竞争同一图层。

## 测量数据

生产产物通过 2026-08-09 的 `pnpm build` 测得。路由数据为排除共享应用外壳后的
独占 JavaScript gzip 体积；它衡量完整参考实现，不等同于孤立库的理论最小体积。

| 实验 | 路由独占 JavaScript | 额外资产 / 异步运行时 | 观察 |
|---|---:|---:|---|
| D3 + Motion | 约 58.9 kB gzip | 无 | 包含 D3 数据几何与 Motion 过渡；React 持有 DOM |
| Lottie | 约 3.3 kB gzip | Lottie Light 约 46.5 kB gzip；示例 JSON 约 2.1 kB（解析后紧凑体积） | 播放引擎在客户端挂载后按需加载 |
| Rive | 约 53.6 kB gzip | Canvas Lite WASM 882,479 B 原始 / 约 330.3 kB gzip；示例 `.riv` 58,792 B | `.riv` 来自官方 CDN，关键产品资产应自托管 |
| Canvas | 约 3.7 kB gzip | 无 | 运行时是浏览器原生 API，主要成本来自绘制工作量 |
| Living Data Story | 约 61.4 kB gzip 首屏 | 复用约 46.5 kB gzip 的 Lottie Light 异步 chunk | D3、Motion、Canvas 与 Lottie 分层组合 |

浏览器参考环境为 Codex 内置 Chromium、1280 × 720 视口、DPR 2、120Hz 显示。
Canvas 在 360 与 720 粒子下均观察到约 120–123 FPS、最近一帧约 8.4ms；这只是
当前桌面设备的参考数据，不代表低端设备、后台标签页或电池供电场景。

## 视觉与交互发现

- D3 的时间范围和用户分群可用原生按钮操作，SVG 之外同步提供最新值、变化方向
  与筛选条件的文字后备。
- Lottie 的分段播放、进度定位和静态模式可正常切换；标准 shape group 是可靠
  渲染的必要资产结构，格式不完整时即使加载成功也可能出现错误色块。
- Rive 官方资产、WASM 和状态机输入均成功加载；Trigger、暂停、重置与静态模式
  行为正常，远程失败时页面保留解释与静态后备。
- Canvas 密度切换不会把逐帧粒子同步进 React；静态模式停止 rAF，但保留完整画面
  与数据说明。
- `prefers-reduced-motion` 与页面静态开关共同生效；旗舰作品在减弱动态效果下保留
  数据、图表、洞察和所有筛选功能。
- 桌面暗色主题下四个实验和旗舰作品均完成目视检查，图层、控件和说明区无遮挡。
  自动化浏览器当前不提供视口调整接口；390px 布局本轮通过响应式代码与内部
  横向滚动边界审读，后续浏览器接口恢复时应补充移动端截图基线。

## 失败模式

- 最初手写的 Lottie JSON 把 ellipse 与 fill 直接放在 shape layer 顶层，加载过程
  没有报错，但关键帧 scale 被错误解析为巨大矩阵，最终显示为整块品牌色。改为
  标准 `group → items → transform` 结构，并移除不完整关键帧后恢复正确图形。
- Rive 的远程 `.riv` 对研究方便，但会把可用性与版本稳定性让给外部 CDN；正式
  产品不能把关键状态反馈只放在该资产中。
- Canvas 的 FPS 会跟随显示器刷新率，因此“120 FPS”不是普适性能分数；帧时间、
  长任务与输入延迟才是跨设备比较的有效指标。

## 技术结论

默认仍从 CSS / SVG + Motion 开始，再按缺失能力增加单一职责图层：

1. D3 负责数据到几何，不默认接管 React DOM 或动画时钟。
2. Motion 负责由 React 状态产生的交互与几何过渡。
3. Lottie 负责线性、预先编排的设计资产；marker 是版本化接口。
4. Rive 负责资产内部的多状态交互；input 名称是版本化接口。
5. Canvas 只负责无语义、高密度、逐帧变化的绘制层。
6. Remotion 与 HyperFrames 属于独立视频输出工程，不与网页运行时竞争位置。

## 可复用候选

- 视觉实验页的结论、职责与反职责结构可以继续复用，但暂不迁入共享 package。
- `DataRange`、`DataSegment` 与确定性数据集目前只有 D3 和旗舰作品两个同仓消费者；
  继续留在 web workspace，等待跨应用消费者出现。
- 静态模式与 `prefers-reduced-motion` 合并逻辑可能成为 motion-kit 候选，但应先在
  v0.5 视频预览或其他真实运行时中验证契约。
