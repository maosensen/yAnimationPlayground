# v0.8 Three.js 空间与 WebGL 动画实验

## 实验问题

Three.js 的价值不在于给二维页面增加“高级感”，而在于提供场景图、透视相机、深度、
材质、光照和空间命中。v0.8 用一个完整参考作品回答三个问题：

1. 什么时候应该从 Canvas 2D 升级到 Three.js？
2. 如何让 React 和 Three.js 各自拥有正确的状态？
3. 如何控制运行时包体、帧预算、减少动效、失败后备与 GPU 资源生命周期？

## 已实现能力

- `/labs/threejs` 是独立路由，Three.js 通过 Client Component 内的动态导入延迟加载；
- `SpatialSignalScene` 集中拥有 renderer、scene、camera、controls、raycaster、点云与清理；
- 三种空间模式共享同一批稳定信号，点云在目标形态之间插值；
- 三个质量档位同时控制点数量和 DPR 上限；
- `renderer.info` 与帧采样每 500ms 才进入 React；
- 射线点击和原生按钮提供等价选择，减少动效会停止循环并保留最终信息；
- 卸载会停止 animation loop、断开 observer / controls，并释放 geometry、material、renderer。

## 关键结论

### Three.js 不是“更强的 Canvas”

Canvas 2D 适合大量屏幕坐标图元；Three.js 适合场景含义依赖三维世界坐标、相机和 GPU
渲染管线。若作品没有这些需求，Three.js 的包体、显存、调试、降级和可访问性成本都
缺少合理回报。

### React 不应驱动每一帧

React 管理模式、选择和策略；Three.js 管理每帧位置与相机。逐帧数据留在 imperative
controller 和 TypedArray 中，比把几千个坐标写入 state 更符合两个系统的职责。

### 清理是功能，不是优化项

路由应用会反复挂载和卸载场景。停止帧循环但不释放 geometry/material 仍会保留 GPU
资源；只释放 renderer 也不等于释放全部用户资源。因此本实验将显式清理作为退出标准。

## 验收记录

2026-08-11 在当前开发机与 Codex 内置 Chromium 完成以下检查：

- 均衡档 1,200 点、1.5× DPR 下观察到约 120 FPS、8.3ms 平均帧时、11 draw
  calls 与 8 个 geometry；刷新率来自当前显示器，不是跨设备性能分数；
- 压力档开启减少动效后，场景停止循环并保持 2,600 点、2× DPR 的最终布局，面板显示
  “静态”而不是沿用上一轮 FPS；
- 信号星群、分层映射、聚焦路径三种模式均可切换；暂停、相机复位、自动环绕、原生
  信号按钮和洞察更新均通过；
- 连续两次从 Three.js 路由切到 Canvas 再返回，场景均重新建立且遥测恢复，未出现重复
  canvas 或失效控制；
- Next.js 生产构建成功，Three.js 0.185.1 运行时位于一个 591,381 B 原始 / 149,484 B
  gzip chunk，仅被 `/labs/threejs` 的 react-loadable manifest 引用；`pnpm three:inspect`
  将该隔离结论变成可重复检查；
- 桌面布局与真实 WebGL 画面已截图观察，标题、控制区、舞台与诊断面板无重叠；当前
  浏览器控制接口不支持精确移动端 viewport，因此移动端结论来自响应式代码审查与生产构建。

所有数字仅代表记录设备与当前浏览器，不作为通用性能承诺。
